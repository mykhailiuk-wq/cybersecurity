# Лабораторна 9. Серверні об'єкти даних і модель Белла-ЛаПадула

Клієнт-серверна програма на Python для роботи з серверними об'єктами даних
(рядки символів і текстові файли) за політикою доступу **«модель
Белла-ЛаПадула без категорій»**. Аутентифікація виконана методом
«рукостискання» з USB-токеном (варіант 10): роль токена безпеки виконує
власний флеш-диск, а вся реєстраційна інформація лежить у файлі
`usb_auth_token.json` у корені носія.

Сервер під час реєстрації зберігає в системній базі даних ідентифікатор
користувача, узгоджену **процедуру перетворення** (хеш-алгоритм Windows
CryptoAPI), допуск і роль. Під час входу сервер генерує випадкове число,
клієнт перетворює його узгодженим алгоритмом, сервер повторює обчислення й
порівнює відповіді. Після успішного рукостискання клієнт працює з об'єктами
в межах **того самого TCP-з'єднання**.

## Що реалізовано

* TCP-сервер (`server.server`), один потік на з'єднання, JSON-повідомлення
  по одному в рядку.
* TCP-клієнт (`client.client`), який читає токен із флеш-диска.
* Реєстрація за одноразовим кодом адміністратора; код визначає допуск і роль.
* Хеш-алгоритми CryptoAPI: MD5, SHA-1, SHA-256, SHA-384, SHA-512.
* Генератор випадкових чисел CryptoAPI (`CryptGenRandom`).
* Серверне сховище об'єктів у SQLite: рядки (`kind=text`) і текстові файли
  (`kind=file`), до 16 КіБ вмісту.
* Дискреційний доступ (ACL): власник має всі права, іншим права призначає
  лише власник через `grant`/`revoke`.
* Мандатна політика Белла-ЛаПадула без категорій (4 рівні секретності).
* Журнал дій (`audit`) із записами про дозволи та відмови.
* Автоматична демонстрація `demo/demo_blp.py`: 4 користувачі, 11 створених
  об'єктів (10 після видалення), 43 кроки протоколу.
* 55 модульних та інтеграційних тестів, зокрема повний цикл через loopback
  `127.0.0.1`.

## Модель доступу

### Рівні секретності

Модель використовує лише рівні (без категорій «need-to-know»), які
утворюють повний порядок:

| Ранг | Назва          | Скорочення |
|------|----------------|------------|
| 1    | `UNCLASSIFIED` | `U`        |
| 2    | `CONFIDENTIAL` | `C`        |
| 3    | `SECRET`       | `S`        |
| 4    | `TOP_SECRET`   | `TS`       |

У командах приймаються назви, скорочення та числа (`1`..`4`), регістр не
важливий; `TOP-SECRET` і `top secret` нормалізуються автоматично.

### Права доступу (5, разом із правом власника)

| Право    | Хто має                          | Призначення                         |
|----------|----------------------------------|-------------------------------------|
| `owner`  | власник об'єкта                  | повний набір прав, не передається   |
| `read`   | власник або ACL                  | читання вмісту                      |
| `append` | власник або ACL                  | дописування в кінець               |
| `write`  | власник або ACL                  | заміна вмісту                       |
| `delete` | власник або ACL                  | видалення об'єкта                   |

Право `owner` не можна видати через ACL: воно виникає лише при створенні
об'єкта й завжди дає власнику `read`, `append`, `write`, `delete`.

### Мандатні правила (BLP без категорій)

Нехай `S` — допуск суб'єкта (користувача), `O` — рівень об'єкта.

| Дія      | Правило            | Пояснення                                  |
|----------|--------------------|--------------------------------------------|
| `read`   | `S >= O`           | no read up — не можна читати вище допуску  |
| `append` | `S <= O`           | no write down — не можна писати нижче      |
| `write`  | `S == O`           | заміна вмісту потребує однакового рівня    |
| `delete` | не обмежується     | класична BLP не регулює знищення           |
| `create` | `O >= S`           | не можна створити об'єкт нижче допуску      |

Мандатні правила діють **поверх ACL**: навіть власник не прочитає власний
об'єкт, якщо його допуск нижчий за рівень об'єкта. Створення об'єкта вище
свого допуску (запис угору) дозволене, але прочитати його автор не зможе.

### Дискреційний рівень (ACL)

Кожен об'єкт має власника. Власник єдиний, хто може призначати (`grant`) або
відбирати (`revoke`) права іншим користувачам. Запис ACL зберігає набір прав
`read`, `append`, `write`, `delete`. Під час кожної операції сервер
перевіряє спочатку наявність права в ACL, потім мандатне правило; відмова на
будь-якому етапі записується до журналу `audit`.

## Як працює протокол

Повідомлення — це JSON-об'єкти, по одному в рядку (UTF-8, до 64 КіБ).

### Реєстрація

```
Клієнт                                          Сервер
  |  enroll {code, id, algorithm, secret,         |
  |          media_serial}                        |
  |---------------------------------------------->|
  |                                               | перевіряє одноразовий код,
  |                                               | бере з нього допуск і роль,
  |                                               | зберігає id + algorithm
  |                                               | + secret + serial у БД
  |  enrolled {user, algorithm, clearance, role}  |
  |<----------------------------------------------|
  | записує usb_auth_token.json на флеш-диск      |
```

Клієнт генерує 256-бітний секрет токена, обирає алгоритм (типово SHA-256) і
передає їх серверу разом з одноразовим кодом. **Допуск і роль задає код**
(`enroll-code --level ... [--admin]`), тому клієнт не може сам собі
підвищити рівень.

### Аутентифікація («рукостискання»)

```
Клієнт                                          Сервер
  |  hello {id, media_serial}                     |
  |---------------------------------------------->|
  |                                               | R = random(32 байти)
  |  challenge {session, nonce=R, expires_in}     |
  |<----------------------------------------------|
  | response = H(R, secret, id)                   |
  |  response {session, mac=response}             |
  |---------------------------------------------->|
  |                                               | обчислює H(R, secret, id)
  |                                               | порівнює за сталий час
  |  result {ok, session, clearance, role, ...}   |
  |<----------------------------------------------|
```

### Робота з об'єктами в тому самому з'єднанні

Після `result {ok: true}` клієнт надсилає запити з ідентифікатором сеансу:

```json
{"type": "object", "proto": 1, "session": "...", "action": "read",
 "name": "s-report"}
```

Сервер відповідає `{"type": "object_result", "ok": true|false, ...}`.
Завершення — `{"type": "bye", "proto": 1}`.

Дії: `whoami`, `list`, `info`, `read`, `create`, `write`, `append`, `delete`,
`grant`, `revoke`, `audit`, `inventory`. Дії `audit` та `inventory` доступні
лише ролі `admin`.

### Процедура перетворення

Для узгодженого алгоритму `H` (наприклад, SHA-256):

```
response = HMAC-H( key = secret_токена,
                   message = "usb-auth-handshake-v1" || 0x00 ||
                             user_id || 0x00 || R )
```

HMAC — стандартна конструкція на основі обраного хешу CryptoAPI. Контекстний
префікс відділяє рукостискання від інших застосувань ключа, а `user_id`
прив'язує відповідь до конкретного облікового запису. Сервер виконує ту саму
операцію з тим самим секретом і порівнює результати через
`hmac.compare_digest`.

| Алгоритм | ALG_ID       | Розмір результату |
|----------|--------------|-------------------|
| MD5      | `0x00008003` | 16 байтів         |
| SHA-1    | `0x00008004` | 20 байтів         |
| SHA-256  | `0x0000800C` | 32 байти          |
| SHA-384  | `0x0000800D` | 48 байтів         |
| SHA-512  | `0x0000800E` | 64 байти          |

MD5 і SHA-1 залишені для демонстрації сумісності з CryptoAPI; для реального
використання слід брати SHA-256 або SHA-512.

## Файл токена

`usb_auth_token.json` у корені флеш-диска:

```json
{
  "format": "usb-auth-token/1",
  "user_id": "alice",
  "algorithm": "SHA256",
  "secret": "oL6JybtTT7lH4uKDso/wGoU8KL2vioMBSadGsR9TYpU=",
  "media_serial": "C8AA0A1D",
  "media_label": "USB DISK",
  "server": "192.168.1.50:5555",
  "created_at": "2026-10-30T10:58:20+00:00",
  "clearance": 4,
  "role": "admin"
}
```

`media_serial` — серійний номер тому (той самий, що показує команда `vol`).
Клієнт відмовляється працювати, якщо файл лежить не на знімному носії або
серійний номер не збігається із записаним. Сервер додатково порівнює
серійний номер, який повідомляє клієнт, зі збереженим у базі.

Поля `clearance` і `role` у токені — лише довідкові для `client info`.
Справжні допуск і роль сервер бере з власної бази під час входу, тому
редагування файлу токена не підвищує права.

## База даних

Файл `data/auth.db` (SQLite) створюється автоматично; старі бази
доповнюються стовпцями `clearance`/`role` під час міграції.

```sql
CREATE TABLE users (
    user_id      TEXT PRIMARY KEY,
    algorithm    TEXT NOT NULL,      -- узгоджена процедура (SHA256 тощо)
    secret       BLOB NOT NULL,      -- секрет токена
    media_serial TEXT,               -- прив'язка до флеш-диска
    created_at   TEXT NOT NULL,
    enabled      INTEGER NOT NULL DEFAULT 1,
    clearance    INTEGER NOT NULL DEFAULT 1,  -- допуск (1..4)
    role         TEXT NOT NULL DEFAULT 'user'
);

CREATE TABLE enroll_codes (
    code       TEXT PRIMARY KEY,     -- одноразовий код реєстрації
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,
    used_at    TEXT,
    used_by    TEXT,
    note       TEXT,
    clearance  INTEGER NOT NULL DEFAULT 1,  -- допуск нового користувача
    is_admin   INTEGER NOT NULL DEFAULT 0   -- роль нового користувача
);

CREATE TABLE objects (
    object_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT NOT NULL UNIQUE, -- ім'я об'єкта
    owner_id   TEXT NOT NULL,        -- власник
    level      INTEGER NOT NULL,     -- рівень секретності 1..4
    kind       TEXT NOT NULL DEFAULT 'text',  -- text | file
    content    TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE acl (
    object_id  INTEGER NOT NULL,
    user_id    TEXT NOT NULL,
    rights     TEXT NOT NULL,        -- "read,append,write,delete"
    granted_by TEXT,
    granted_at TEXT NOT NULL,
    PRIMARY KEY (object_id, user_id)
);

CREATE TABLE audit (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    at          TEXT NOT NULL,
    user_id     TEXT,
    action      TEXT NOT NULL,
    object_name TEXT,
    allowed     INTEGER NOT NULL,
    reason      TEXT NOT NULL DEFAULT ''
);
```

При видаленні об'єкта записи ACL видаляються каскадно; користувача, який
володіє об'єктами, видалити не можна, доки об'єкти не видалені.

## Швидкий старт: loopback 127.0.0.1

Відкрийте **два** термінали в корені проєкту (`D:\cybersecurity\lab9`).

Термінал 1 — сервер:

```powershell
python -m server.server --db data/auth.db run --host 127.0.0.1 --port 5555
```

Термінал 2 — видати одноразовий код реєстрації (діє 15 хвилин). Код задає
допуск і, за потреби, роль адміністратора:

```powershell
python -m server.server --db data/auth.db enroll-code --ttl 900 `
    --level SECRET --note "student10"
```

Приклад виводу:

```
Одноразовий код реєстрації: ABCD-1234-EF56-7890
Допуск: SECRET; роль: user
Дійсний протягом 900 с. Передайте його користувачу.
```

Для перевірки без флеш-диска використайте каталог і прапорець
`--allow-fixed` (дозволяє незнімний носій):

```powershell
mkdir C:\temp\usb-token
python -m client.client register --server 127.0.0.1:5555 `
    --token C:\temp\usb-token --id student10 `
    --code ABCD-1234-EF56-7890 --algorithm SHA256 --allow-fixed
```

Вхід, перевірка допуску та робота з об'єктами:

```powershell
python -m client.client login  --token C:\temp\usb-token --allow-fixed
python -m client.client whoami --token C:\temp\usb-token --allow-fixed

# створити рядок рівня SECRET
python -m client.client create --token C:\temp\usb-token --allow-fixed `
    --name my-note --level SECRET --text "перший рядок" 

# створити об'єкт з текстового файлу (kind=file)
python -m client.client create --token C:\temp\usb-token --allow-fixed `
    --name imported --level SECRET --file C:\temp\note.txt

python -m client.client ls       --token C:\temp\usb-token --allow-fixed
python -m client.client read     --token C:\temp\usb-token --allow-fixed --name my-note
python -m client.client append   --token C:\temp\usb-token --allow-fixed `
    --name my-note --text "`nдругий рядок"
python -m client.client objinfo  --token C:\temp\usb-token --allow-fixed --name my-note
```

Приклад успішного входу:

```
[OK] Аутентифікацію пройдено: student10
     Допуск: SECRET; роль: user
     Алгоритм: SHA256; сервер: 127.0.0.1:5555
```

Перегляд токена (секрет не показується):

```powershell
python -m client.client info --token C:\temp\usb-token
```

Список користувачів, об'єктів і журнал на сервері:

```powershell
python -m server.server --db data/auth.db users
python -m server.server --db data/auth.db objects
python -m server.server --db data/auth.db audit --limit 50
```

### Приклад сценарію з двома користувачами

Нехай `alice` має допуск `TOP_SECRET`, а `bob` — `SECRET` (коди видаються
окремо, як показано вище). `bob` створює об'єкт `s-report` рівня `SECRET` і
надає `alice` право `read`:

```powershell
python -m client.client create --token C:\temp\token-bob --allow-fixed `
    --name s-report --level SECRET --text "звіт"

python -m client.client grant --token C:\temp\token-bob --allow-fixed `
    --name s-report --id alice --rights read

python -m client.client read --token C:\temp\token-alice --allow-fixed `
    --name s-report
```

Спроба `alice` дописати в `s-report` (запис униз, `TOP_SECRET -> SECRET`)
буде відхилена навіть після `grant ... --rights append`:

```
[DENY] append s-report: no-write-down: clearance TOP_SECRET > classification SECRET
```

### Робота з реальним флеш-диском

Нехай носій підключено як `E:`. Прапорець `--allow-fixed` **не потрібен** —
клієнт перевірить, що це знімний носій, і запише його серійний номер у токен.

```powershell
python -m client.client register --server 127.0.0.1:5555 `
    --token E:\ --id student10 --code ABCD-1234-EF56-7890

python -m client.client login --token E:\
```

Якщо флеш-диск визначається Windows як «fixed» (буває з деякими USB-HDD),
для налагодження можна додати `--allow-fixed`, але прив'язка до серійного
номера все одно перевіряється.

## Автоматична демонстрація

Скрипт сам піднімає TCP-сервер на loopback, реєструє 4 користувачів з
різними допусками, створює 11 об'єктів і виконує дозволені та заборонені
операції. Повний протокол записується у `logs/lab9_protocol.log`.

```powershell
python demo/demo_blp.py
```

| Користувач | Допуск        | Роль    | Що демонструє                                  |
|------------|---------------|---------|------------------------------------------------|
| `alice`    | `TOP_SECRET`  | `admin` | інвентаризацію, журнал, читання вниз           |
| `bob`      | `SECRET`      | `user`  | власник об'єктів, призначення прав             |
| `carol`    | `CONFIDENTIAL`| `user`  | читання вниз, дописування вгору, відмови       |
| `dave`     | `UNCLASSIFIED`| `user`  | дописування вгору, заборона читання вище       |

Демонстрація перевіряє, зокрема: відсутність права в ACL, `no-read-up`,
`no-write-down`, потребу однакового рівня для `write`, заборону створення
вниз, дозвіл створення вгору, `delete` без мандатних обмежень, `grant`/
`revoke`, інвентаризацію та журнал адміністратора.

Демо-дані створюються у `data/lab9-demo/` (база й токени), тому їх можна
безпечно видалити й запустити демонстрацію знову.

## Запуск на двох комп'ютерах

1. На **серверному** комп'ютері дізнайтеся IP-адресу в локальній мережі:

   ```powershell
   ipconfig
   ```

   Нехай це `192.168.1.50`.

2. Запустіть сервер на всіх інтерфейсах (типово він слухає лише
   `127.0.0.1`, тому віддалені клієнти не підключаться):

   ```powershell
   python -m server.server --db data/auth.db run --host 0.0.0.0 --port 5555
   ```

3. Відкрийте TCP-порт 5555 у брандмауері Windows (термінал адміністратора):

   ```powershell
   New-NetFirewallRule -DisplayName "BLP Lab 9 Server 5555" `
       -Direction Inbound -Protocol TCP -LocalPort 5555 `
       -Action Allow -Profile Private
   ```

4. На **клієнтському** комп'ютері перевірте доступність сервера:

   ```powershell
   ping 192.168.1.50
   Test-NetConnection 192.168.1.50 -Port 5555
   ```

5. Видайте код на сервері (допуск і роль задаються тут):

   ```powershell
   python -m server.server --db data/auth.db enroll-code --ttl 900 --level SECRET
   ```

6. На клієнтському комп'ютері зареєструйте флеш-диск (код — з попереднього
   кроку):

   ```powershell
   python -m client.client register --server 192.168.1.50:5555 `
       --token E:\ --id student10 --code ABCD-1234-EF56-7890
   ```

7. Працюйте з об'єктами (адресу сервера клієнт бере з файлу токена):

   ```powershell
   python -m client.client login --token E:\
   python -m client.client ls    --token E:\
   python -m client.client read  --token E:\ --name shared-note
   ```

   або явно вкажіть сервер:

   ```powershell
   python -m client.client whoami --token E:\ --server 192.168.1.50:5555
   ```

Після успішного входу в журналі сервера з'явиться рядок
`AUTH OK user=student10 peer=192.168.1.23:... level=SECRET role=user`, а в
журналі клієнта — `[OK] Аутентифікацію пройдено`.

## Командний рядок

Параметр `--db` є глобальним і стоїть **перед** назвою підкоманди.

### Сервер

```powershell
python -m server.server --db data/auth.db run --host 127.0.0.1 --port 5555

# видати код; --level приймає назву або число, --admin робить адміністратором
python -m server.server --db data/auth.db enroll-code --ttl 900 --level SECRET --note "Іваненко"
python -m server.server --db data/auth.db enroll-code --level TOP_SECRET --admin

python -m server.server --db data/auth.db users
python -m server.server --db data/auth.db objects
python -m server.server --db data/auth.db acl --object s-report
python -m server.server --db data/auth.db audit --limit 50

python -m server.server --db data/auth.db set-level --id student10 --level CONFIDENTIAL
python -m server.server --db data/auth.db set-role  --id student10 --role admin
python -m server.server --db data/auth.db enable    --id student10
python -m server.server --db data/auth.db disable   --id student10
python -m server.server --db data/auth.db object-remove --name s-report
python -m server.server --db data/auth.db remove    --id student10
```

`object-remove` — аварійне видалення об'єкта адміністратором; звичайне
видалення виконується клієнтом із дотриманням ACL.

### Клієнт

| Команда            | Призначення                                             |
|--------------------|---------------------------------------------------------|
| `register`         | зареєструвати токен за одноразовим кодом                |
| `login`            | пройти рукостискання                                    |
| `info`             | показати вміст токена без секрету                       |
| `whoami`           | показати допуск і роль на сервері                       |
| `ls`               | об'єкти, доступні користувачу                           |
| `read`             | прочитати об'єкт                                        |
| `create`           | створити об'єкт (`--text` або `--file`)                 |
| `write`            | замінити вміст                                          |
| `append`           | дописати в кінець                                       |
| `delete`           | видалити об'єкт                                         |
| `grant`            | призначити права (`--id`, `--rights`)                   |
| `revoke`           | відібрати права (без `--rights` — усі)                  |
| `objinfo`          | метадані, права та ACL об'єкта                          |
| `export`           | зберегти прочитаний об'єкт у локальний файл             |
| `inventory`        | усі об'єкти сервера (лише `admin`)                      |
| `audit`            | журнал дій (лише `admin`)                               |

Усі команди роботи з об'єктами приймають `--token`, `--allow-fixed`,
`--server` і `--timeout`.

## Тести

```powershell
python -m unittest discover -s tests -v
```

55 тестів піднімають справжній TCP-сервер на випадковому порту loopback і
перевіряють:

* реєстрацію та успішний вхід, роботу всіх п'яти хеш-алгоритмів;
* відмову при неправильному секреті та для невідомого користувача;
* одноразовість кодів реєстрації та прив'язку до серійного номера носія;
* заборону повторного відтворення перехопленої відповіді;
* блокування після п'яти невдалих спроб;
* мандатні правила BLP: `no-read-up`, `no-write-down`, рівність для `write`,
  заборону створення вниз і дозвіл створення вгору;
* дискреційний доступ: власник має всі права, `grant`/`revoke`, відмову без
  ACL, каскадне видалення об'єкта;
* журнал `audit` та інвентаризацію адміністратора;
* командний рядок клієнта для повного циклу об'єктів.

## Безпека: що саме забезпечено

* **Одноразові коди реєстрації** з обмеженим терміном дії; код не можна
  використати двічі навіть при паралельних запитах (атомарна транзакція).
* **Допуск і роль задає сервер** через код реєстрації, а не клієнт.
* **Новий випадковий виклик у кожному сеансі** (32 байти з `CryptGenRandom`),
  тому перехоплена відповідь не підходить для повторного входу.
* **Порівняння за сталий час** (`hmac.compare_digest`).
* **Однакова відповідь для невідомого користувача та хибного секрета**, щоб не
  розкривати наявність облікового запису.
* **Блокування** після 5 невдалих спроб протягом 10 хвилин (на 5 хвилин).
* **Прив'язка до носія**: клієнт перевіряє знімний носій і серійний номер тому,
  сервер — серійний номер, повідомлений клієнтом.
* **Двоетапна перевірка доступу**: спочатку ACL, потім мандатні правила BLP;
  відмови журналюються.
* **Ізоляція даних**: вміст об'єктів зберігається лише на сервері, клієнт не
  має прямого доступу до файлової системи сервера.
* **Тільки сервер** зберігає ідентифікатор і процедуру перетворення; клієнт
  отримує лише випадкове число.

### Свідомі обмеження навчальної реалізації

* Немає TLS: під час реєстрації секрет токена передається мережею у
  відкритому вигляді, а після входу вміст об'єктів також іде без шифрування.
  Для реальної експлуатації потрібен TLS або захищений канал. На loopback і в
  довіреній локальній мережі це прийнятно для лабораторної роботи.
* Секрет токена зберігається в базі даних у відкритому вигляді (інакше сервер
  не зможе обчислити очікувану відповідь). Базу слід захищати засобами ОС.
* `CryptGenRandom` — застаріла, але саме CryptoAPI-функція; на сучасних
  Windows вона реалізована через BCryptGenRandom. Якщо виклик недоступний,
  використовується `os.urandom`.
* Серійний номер тому можна підробити, а файл токена — скопіювати разом із
  підміною номера; це властивість звичайної флешки, а не смарт-картки.
* Вміст об'єкта обмежений 16 КіБ, щоб повідомлення протоколу вкладалося в
  ліміт 64 КіБ.
* MD5 і SHA-1 не рекомендовані для реального застосування.

## Типові проблеми

| Симптом | Причина та рішення |
|---------|--------------------|
| `не вдалося підключитися до ...` | сервер не запущено, інший порт або брандмауер |
| клієнт на іншому ПК не бачить сервер | сервер слухає `127.0.0.1`; запустіть із `--host 0.0.0.0` |
| `... не є знімним носієм` | вказано каталог на диску C:; підключіть флешку або додайте `--allow-fixed` |
| `код реєстрації вже використано` | видайте новий код командою `enroll-code` |
| `користувач ... вже зареєстрований` | видаліть запис (`remove --id ...`) або оберіть інший id |
| `серійний номер носія ... не збігається` | файл токена скопійовано на інший носій |
| `[DENY] ... no-read-up` | допуск нижчий за рівень об'єкта; це мандатна політика |
| `[DENY] ... no-write-down` | спроба запису вниз; потрібен об'єкт не нижче допуску |
| `[DENY] ... дискреційна відмова` | власник не надав відповідного права через `grant` |
| `[DENY] ... лише адміністратор` | `inventory`/`audit` доступні ролі `admin` |
| `[FAIL] ... too many failed attempts` | спрацювало блокування; зачекайте 5 хвилин |
| порт зайнятий | змініть `--port` на сервері та в адресі клієнта |
