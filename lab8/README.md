# Варіант 10. Аутентифікація методом «рукостискання» з USB-токеном

Лабораторна робота: клієнт-серверна система аутентифікації за протоколом
TCP/IP. Роль токена безпеки виконує власний флеш-диск: уся реєстраційна
інформація, потрібна для входу, лежить у файлі `usb_auth_token.json` у корені
носія.

Сервер під час реєстрації зберігає в системній базі даних ідентифікатор
користувача та узгоджену **процедуру перетворення** (один із хеш-алгоритмів
Windows CryptoAPI). Під час входу сервер генерує випадкове число, клієнт
перетворює його узгодженим алгоритмом і повертає результат; сервер виконує ту
саму операцію та порівнює відповіді.

## Що реалізовано

* TCP-сервер на Python (модуль `server.server`), один потік на з'єднання.
* TCP-клієнт (`client.client`), який читає токен із флеш-диска.
* Реєстрація за одноразовим кодом, який видає адміністратор.
* База даних SQLite: ідентифікатор, алгоритм, секрет токена, серійний номер
  носія.
* Хеш-алгоритми CryptoAPI: MD5, SHA-1, SHA-256, SHA-384, SHA-512.
* Генератор випадкових чисел CryptoAPI (`CryptGenRandom`).
* Захист від повторного відтворення відповіді, від перебору та від
  використання файлу токена на іншому носії.
* Модульні й інтеграційні тести (29 тестів), зокрема повний цикл через
  loopback `127.0.0.1`.

## Структура проєкту

```
common/crypto.py      хеш-алгоритми CryptoAPI, HMAC-перетворення, RNG
common/media.py       тип носія та серійний номер тому (Windows API)
common/protocol.py    кадрування JSON-повідомлень, валідація, адреси
common/util.py        робота з часом UTC
server/db.py          схема та операції бази даних SQLite
server/server.py      TCP-сервер, рукостискання, реєстрація, CLI
client/token_file.py  файл токена, перевірка знімного носія
client/client.py      TCP-клієнт, рукостискання, реєстрація, CLI
tests/                тести криптографії, протоколу та інтеграції
```

Залежностей немає: потрібен лише Python 3.9+ зі стандартною бібліотекою.

## Як працює протокол

Повідомлення — це JSON-об'єкти, по одному в рядку (UTF-8, до 64 КіБ).

### Реєстрація

```
Клієнт                                          Сервер
  |  enroll {code, id, algorithm, secret,         |
  |          media_serial}                        |
  |---------------------------------------------->|
  |                                               | перевіряє одноразовий код,
  |                                               | зберігає id + algorithm
  |                                               | + secret + serial у БД
  |  enrolled {user, algorithm}                   |
  |<----------------------------------------------|
  | записує usb_auth_token.json на флеш-диск      |
```

Клієнт сам генерує 256-бітний секрет токена, обирає алгоритм (за
замовчуванням SHA-256) і передає їх серверу разом з одноразовим кодом.
Сервер зберігає в базі саме **процедуру** (назву алгоритму) та секрет, з
яким ця процедура застосовується.

### Аутентифікація («рукостискання»)

```
Клієнт                                          Сервер
  |  hello {id, media_serial}                     |
  |---------------------------------------------->|
  |                                               | R = random(32 байти)
  |  challenge {session, nonce=R, expires_in}     |
  |<----------------------------------------------|
  | response = H(R, secret, id)                   |
  |  response {session, mac=response}             |
  |---------------------------------------------->|
  |                                               | обчислює H(R, secret, id)
  |                                               | порівнює за сталий час
  |  result {ok: true/false, ...}                 |
  |<----------------------------------------------|
```

### Процедура перетворення

Для узгодженого алгоритму `H` (наприклад, SHA-256):

```
response = HMAC-H( key = secret_токена,
                   message = "usb-auth-handshake-v1" || 0x00 ||
                             user_id || 0x00 || R )
```

HMAC — стандартна конструкція на основі обраного хешу CryptoAPI. Контекстний
префікс відділяє рукостискання від інших застосувань ключа, а `user_id`
прив'язує відповідь до конкретного облікового запису. Сервер виконує ту саму
операцію з тим самим секретом і порівнює результати через
`hmac.compare_digest`.

Ідентифікатори CryptoAPI, які підтримуються:

| Алгоритм | ALG_ID       | Розмір результату |
|----------|--------------|-------------------|
| MD5      | `0x00008003` | 16 байтів         |
| SHA-1    | `0x00008004` | 20 байтів         |
| SHA-256  | `0x0000800C` | 32 байти          |
| SHA-384  | `0x0000800D` | 48 байтів         |
| SHA-512  | `0x0000800E` | 64 байти          |

MD5 і SHA-1 залишені для демонстрації сумісності з CryptoAPI; для реального
використання слід брати SHA-256 або SHA-512.

## Файл токена

`usb_auth_token.json` у корені флеш-диска:

```json
{
  "format": "usb-auth-token/1",
  "user_id": "student10",
  "algorithm": "SHA256",
  "secret": "oL6JybtTT7lH4uKDso/wGoU8KL2vioMBSadGsR9TYpU=",
  "media_serial": "C8AA0A1D",
  "media_label": "USB DISK",
  "server": "192.168.1.50:5555",
  "created_at": "2026-10-30T10:58:20+00:00"
}
```

`media_serial` — серійний номер тому (той самий, що показує команда `vol`).
Клієнт відмовляється працювати, якщо файл лежить не на знімному носії або
серійний номер не збігається із записаним. Сервер додатково порівнює
серійний номер, який повідомляє клієнт, зі збереженим у базі.

## База даних

Файл `data/auth.db` (SQLite) створюється автоматично.

```sql
CREATE TABLE users (
    user_id      TEXT PRIMARY KEY,
    algorithm    TEXT NOT NULL,      -- узгоджена процедура (SHA256 тощо)
    secret       BLOB NOT NULL,      -- секрет токена
    media_serial TEXT,               -- прив'язка до флеш-диска
    created_at   TEXT NOT NULL,
    enabled      INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE enroll_codes (
    code       TEXT PRIMARY KEY,     -- одноразовий код реєстрації
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,
    used_at    TEXT,
    used_by    TEXT,
    note       TEXT
);
```

## Швидкий старт: loopback 127.0.0.1

Відкрийте **два** термінали в корені проєкту.

Термінал 1 — сервер:

```powershell
python -m server.server --db data/auth.db run --host 127.0.0.1 --port 5555
```

Термінал 2 — видати одноразовий код реєстрації (код діє 15 хвилин):

```powershell
python -m server.server --db data/auth.db enroll-code --ttl 900 --note "student10"
```

Приклад виводу:

```
Одноразовий код реєстрації: ABCD-1234-EF56-7890
```

Далі — реєстрація токена. Для перевірки без флеш-диска використайте каталог
і прапорець `--allow-fixed` (він дозволяє незнімний носій):

```powershell
mkdir C:\temp\usb-token
python -m client.client register --server 127.0.0.1:5555 `
    --token C:\temp\usb-token --id student10 `
    --code ABCD-1234-EF56-7890 --algorithm SHA256 --allow-fixed
```

Вхід:

```powershell
python -m client.client login --token C:\temp\usb-token --allow-fixed
```

Очікуваний результат:

```
[OK] Аутентифікацію пройдено: student10
     Алгоритм: SHA256; сервер: 127.0.0.1:5555
```

Перегляд токена (секрет не показується):

```powershell
python -m client.client info --token C:\temp\usb-token
```

Список користувачів на сервері:

```powershell
python -m server.server --db data/auth.db users
```

### Робота з реальним флеш-диском

Нехай носій підключено як `E:`. Прапорець `--allow-fixed` **не потрібен** —
клієнт перевірить, що це знімний носій, і запише його серійний номер у токен.

```powershell
python -m client.client register --server 127.0.0.1:5555 `
    --token E:\ --id student10 --code ABCD-1234-EF56-7890

python -m client.client login --token E:\
```

Якщо флеш-диск визначається Windows як «fixed» (так буває з деякими
USB-HDD), для налагодження можна додати `--allow-fixed`, але прив'язка до
серійного номера все одно перевіряється.

## Запуск на двох комп'ютерах

1. На **серверному** комп'ютері дізнайтеся IP-адресу в локальній мережі:

   ```powershell
   ipconfig
   ```

   Нехай це `192.168.1.50`.

2. Запустіть сервер на всіх інтерфейсах (за замовчуванням він слухає лише
   `127.0.0.1`, тому віддалені клієнти не підключаться):

   ```powershell
   python -m server.server --db data/auth.db run --host 0.0.0.0 --port 5555
   ```

3. Відкрийте TCP-порт 5555 у брандмауері Windows (термінал адміністратора):

   ```powershell
   New-NetFirewallRule -DisplayName "USB Auth Server 5555" `
       -Direction Inbound -Protocol TCP -LocalPort 5555 `
       -Action Allow -Profile Private
   ```

4. На **клієнтському** комп'ютері перевірте доступність сервера:

   ```powershell
   ping 192.168.1.50
   Test-NetConnection 192.168.1.50 -Port 5555
   ```

5. Видайте код на сервері:

   ```powershell
   python -m server.server --db data/auth.db enroll-code --ttl 900
   ```

6. На клієнтському комп'ютері зареєструйте флеш-диск (код — з попереднього
   кроку):

   ```powershell
   python -m client.client register --server 192.168.1.50:5555 `
       --token E:\ --id student10 --code ABCD-1234-EF56-7890
   ```

7. Вхід із токена (адресу сервера клієнт бере з файлу токена):

   ```powershell
   python -m client.client login --token E:\
   ```

   або явно:

   ```powershell
   python -m client.client login --token E:\ --server 192.168.1.50:5555
   ```

Після успішного входу в журналі сервера з'явиться рядок
`AUTH OK user=student10 peer=192.168.1.23:...`, а в журналі клієнта —
`[OK] Аутентифікацію пройдено`.

## Керування користувачами

```powershell
# видати новий одноразовий код
python -m server.server --db data/auth.db enroll-code --ttl 900 --note "Іваненко"

# список
python -m server.server --db data/auth.db users

# вимкнути / увімкнути
python -m server.server --db data/auth.db disable --id student10
python -m server.server --db data/auth.db enable  --id student10

# видалити (після цього можна зареєструвати той самий id знову)
python -m server.server --db data/auth.db remove --id student10
```

Параметр `--db` є глобальним і стоїть **перед** назвою команди.

## Тести

```powershell
python -m unittest discover -s tests -v
```

Тести піднімають справжній TCP-сервер на випадковому порту loopback і
перевіряють:

* реєстрацію та успішний вхід;
* роботу всіх п'яти хеш-алгоритмів;
* відмову при неправильному секреті та для невідомого користувача;
* одноразовість кодів реєстрації;
* заборону повторного відтворення перехопленої відповіді;
* прив'язку до серійного номера носія;
* блокування після п'яти невдалих спроб;
* роботу командного рядка клієнта.

## Безпека: що саме забезпечено

* **Одноразові коди реєстрації** з обмеженим терміном дії; код не можна
  використати двічі навіть при паралельних запитах (атомарна транзакція).
* **Новий випадковий виклик у кожному сеансі** (32 байти з `CryptGenRandom`),
  тому перехоплена відповідь не підходить для повторного входу.
* **Порівняння за сталий час** (`hmac.compare_digest`).
* **Однакова відповідь для невідомого користувача та хибного секрета**, щоб не
  розкривати наявність облікового запису.
* **Блокування** після 5 невдалих спроб протягом 10 хвилин (на 5 хвилин).
* **Прив'язка до носія**: клієнт перевіряє знімний носій і серійний номер тому,
  сервер — серійний номер, повідомлений клієнтом.
* **Тільки сервер** зберігає ідентифікатор і процедуру перетворення; клієнт
  отримує лише випадкове число.

### Свідомі обмеження навчальної реалізації

* Немає TLS: під час реєстрації секрет токена передається мережею у
  відкритому вигляді. Для реальної експлуатації потрібен TLS або реєстрація
  безпосередньо на сервері. На loopback і в довіреній локальній мережі це
  прийнятно для лабораторної роботи.
* Секрет токена зберігається в базі даних у відкритому вигляді (інакше сервер
  не зможе обчислити очікувану відповідь). Базу слід захищати засобами ОС.
* `CryptGenRandom` — застаріла, але саме CryptoAPI-функція; на сучасних
  Windows вона реалізована через BCryptGenRandom. Якщо виклик недоступний,
  використовується `os.urandom`.
* Серійний номер тому можна підробити, а файл токена — скопіювати разом із
  підміною номера; це властивість звичайної флешки, а не смарт-картки.
* MD5 і SHA-1 не рекомендовані для реального застосування.

## Відповідність вимогам варіанта

| Вимога | Реалізація |
|--------|------------|
| Серверна частина, що перевіряє | `server.server`, SQLite-база `server.db` |
| Клієнтська частина, яку перевіряють | `client.client`, файл токена `client.token_file` |
| Взаємодія за TCP/IP | `socketserver` / `socket`, JSON-повідомлення |
| Токен безпеки — власний флеш-диск | файл `usb_auth_token.json` + перевірка знімного носія |
| Уся реєстраційна інформація у файлі на токені | id, алгоритм, секрет, серійний номер, адреса сервера |
| У БД зберігається id та процедура перетворення | таблиця `users` (`user_id`, `algorithm`) |
| Сервер генерує випадкове число | `CryptGenRandom`, 32 байти на сеанс |
| Клієнт перетворює число узгодженим алгоритмом | HMAC на основі обраного хешу CryptoAPI |
| Сервер виконує ту саму операцію й порівнює | `compute_response` + `hmac.compare_digest` |
| Алгоритм хешування з CryptoAPI | MD5, SHA-1, SHA-256, SHA-384, SHA-512 |
| Генератор випадкових чисел з CryptoAPI | `advapi32.CryptGenRandom` |
| Налагодження на loopback 127.0.0.1 | типові команди вище, інтеграційні тести |
| Запуск на двох комп'ютерах | `--host 0.0.0.0`, правила брандмауера, `--server <IP>:5555` |

## Типові проблеми

| Симптом | Причина та рішення |
|---------|--------------------|
| `не вдалося підключитися до ...` | сервер не запущено, інший порт або брандмауер |
| клієнт на іншому ПК не бачить сервер | сервер слухає `127.0.0.1`; запустіть із `--host 0.0.0.0` |
| `... не є знімним носієм` | вказано каталог на диску C:; підключіть флешку або додайте `--allow-fixed` |
| `код реєстрації вже використано` | видайте новий код командою `enroll-code` |
| `користувач ... вже зареєстрований` | видаліть запис (`remove --id ...`) або оберіть інший id |
| `серійний номер носія ... не збігається` | файл токена скопійовано на інший носій |
| `[FAIL] ... too many failed attempts` | спрацювало блокування; зачекайте 5 хвилин |
| порт зайнятий | змініть `--port` на сервері та в адресі клієнта |
